# Tooling trust boundaries

Current assets are maintained source, exact metadata/schema/lock identities and scoped infrastructure reports. Reviewed executable policy and its independently pinned schema are trusted. Received JSON cannot choose an executable, repository identity, plugin or weaker policy.

The implemented input boundary refuses duplicate keys, nonfinite values, invalid UTF-8, unpaired surrogates, oversized files and linked/nonregular inputs. Fixed authored diagnostics avoid echoing confidential values. Accepted metadata precedes exclusive output creation; verification never replaces an inventory.

The tooling assumes a stable ordinary local filesystem and reviewed environment. It does not sandbox hostile concurrent filesystem changes, operating-system compromise or power loss. Static checks do not establish argument relevance, human review, instrument fitness, safety or certification.

Future composition requires complete typed graph and source/scope/current evidence admission. Context padding, hidden OPEN claims, irrelevant references, omitted counterevidence and unsupported notation cannot produce complete coverage. Evidence integrity alone cannot supply relevance or sufficiency.

Future human statements must bind exact immutable content, scope, reviewer, role, purpose and current trust. They cannot be manufactured by the tool or carried forward to changed content. Content, detached review and export remain separate without circular future references. Every rendered/exported view must retain the same gaps, scope and limitations.
